# 5CCSAKNE Coursework 2

Knowledge Engineering coursework: a knowledge graph of UK parliamentary and government policy events reported in UK news between 6 March 2026 and 6 April 2026, built from structured and unstructured sources.

## Reproducing the Submitted Run (examiners start here)

The pipeline is designed to be reproduced **offline from cached snapshots**. No API keys are required. Run:

```bash
python -m venv .venv
source .venv/bin/activate        # Windows: .venv\Scripts\activate
pip install -r requirements.txt
python -m spacy download en_core_web_sm

python -m src.main --from-cache
```

### Required cached artefacts

`--from-cache` reads from two directories that must be present at the repo root:

- `data/raw/{guardian,parliament,govuk,wikidata}/` — source API snapshots used as the input to normalisation and extraction.
- `data/cache/openai/` — cached OpenAI responses for the LLM-assisted extraction (Stage 3) and the RAG completion step (Stage 9). With this cache present, the pipeline runs fully offline and produces the same triples as the submitted run. Without it, Stage 3 will fall back to heuristics only and Stage 9 will skip RAG enrichment, so the completed graph will differ.

If either directory is shipped as a separate archive, unpack it at the repo root before running the command above.

### What to look for after the run

The current pipeline keeps the latest final artefacts in `output/`:

- `output/completed_kg.ttl` — the final knowledge graph.
- `output/query_results.json` — row counts and bindings for all 20 competency queries (expected: `20/20` queries return at least one row).
- `output/validation_results.json` — SPARQL-based graph validation report (expected: `0` violations).
- `output/completion_audit.json` — per-event summary of links added during Stage 9 completion.
- `output/kg_summary.json` — headline metrics (triple counts, coverage, completion deltas).

Processed JSON files in `data/processed/` still keep a UTC timestamp prefix for each run.

## Data Sources

- **Guardian API** — UK politics and policy reporting, full article text.
- **UK Parliament / Hansard written statements API** — official parliamentary source records.
- **GOV.UK Search API** — government policy, guidance, announcements, speeches, consultations, press releases.
- **Wikidata** — optional enrichment for UK politicians, parties, and government bodies via SPARQL.

## Repository Structure

- `src/` — ingestion, extraction, RDF mapping, completion, SPARQL execution, validation.
- `ontology/news_ontology.ttl` — event-centred TBox (generated by `src/build_ontology.py`).
- `queries/news_competency_queries.rq` — 20 SPARQL competency queries.
- `kg/` — generated Turtle outputs (prototype and completed KG).
- `docs/` — competency questions, mapping specification, completion analysis, evaluation methodology and results.
- `tests/` — automated pytest suite covering ontology, extraction, RDF, completion, queries, and validation.
- `data/` — cached raw API snapshots (`raw/`) and cached LLM responses (`cache/`). Required for `--from-cache`.

## Pipeline Stages

`src/main.py` runs 12 stages end to end:

1. **Collect** — fetch Guardian articles, Parliament written statements, GOV.UK records, and optional Wikidata enrichment (or load cached snapshots under `--from-cache`).
2. **Normalise sources** — convert source payloads into a shared record format.
3. **Extract** — extract KG-ready policy-event records from article text, combining controlled-list and regex heuristics, spaCy NER, and schema-validated OpenAI extraction.
4. **Normalise extracted records** — validate and clean extracted event, actor, institution, topic, location, article, and source-record fields.
5. **Build ontology** — programmatically construct the event-centred TBox in `ontology/news_ontology.ttl`.
6. **Map source records to RDF** — convert KG-ready records into article, policy-event, institution, topic, location, and source-record triples.
7. **Map Wikidata to RDF** — directly map structured Wikidata entities to RDF.
8. **Merge** — combine ontology, source-derived instances, and Wikidata into `kg/generated/prototype_kg.ttl`.
9. **Enrich / complete** — three sub-steps: (a) add `news:reportsOn` inverse links, (b) add `news:matchedToSourceRecord` cross-source matches, (c) RAG step that proposes missing `news:involvesActor` / `news:involvesGovernmentBody` / `news:concernsPolicyTopic` links, grounded in retrieved KG context and validated against a closed vocabulary and institutional blocklist. Writes `kg/generated/completed_kg.ttl`.
10. **Query** — run the 20 SPARQL competency queries against the completed KG and save results.
11. **Validate** — run SPARQL-based graph validation rules and save a violations report.
12. **Summarise** — write a completion audit and a KG summary (triple counts, coverage, completion deltas) to `output/`.

## Live-API Mode (not required for marking)

To re-collect data from live APIs instead of using the shipped cache:

```bash
cp .env.example .env    # then fill in GUARDIAN_API_KEY and OPENAI_API_KEY
python -m src.main
```

Parliament, GOV.UK, and Wikidata do not require API keys.

Useful flags:

- `--skip-wikidata` — skip the Wikidata enrichment stage.
- `--wikidata-snapshot PATH` — use a specific cached Wikidata snapshot.
- `--no-save-snapshots` — do not write fresh raw snapshots during live collection.
