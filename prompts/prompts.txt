Prompt Log

These prompts cover KE tasks. Ontology design, pipeline logic, and query structure were the group's work, not generated.


P01: Competency Question Augmentation
Technique: zero-shot with constraint list

Prompt:
We have 10 manually written CQs for a UK parliamentary and government policy event KG. Generate 10 complementary questions that: 
1. stay in the same domain 
2. are answerable from a KG with policy events, actors, parties, departments, bodies, topics, source records, and articles 
3. do not repeat the manual set 
4. vary across aggregation, comparison, co-occurrence, and cross-source linkage.
Return a numbered list with one-line justifications.

Justification: the manual set risked clustering around similar retrieval patterns; the constraint list directed the LLM toward aggregation and cross-source styles it lacked.

Output: 10 draft questions reviewed against the final ontology vocabulary. Several were rewritten to remove vague article-metadata questions that did not test event or institution relations, and author-frequency questions with no event-model grounding were dropped. Removing those shaped the final CQ set and the property names expected in the SPARQL queries.

Used for: docs/competency_questions.md


P02: Ontology Review Against Reused Vocabularies
Technique: zero-shot structured review

Prompt:
Review this ontology draft reusing Schema.org and BBC Core Concepts. Identify: 
1. classes needing more explicit alignment 
2. properties to convert to typed subproperties 
3. missing publisher/organisation distinctions 
4. defined terms absent from the generated RDF
Return concrete issues, a revised alignment proposal, and minimum code changes.

Justification: checking every local term against two external vocabularies manually risks missing gaps; the structured prompt forced a systematic pass across all classes and properties.

Output: a revised alignment table and code change list. Subproperty conversions were implemented in build_ontology.py and json_to_rdf.py, introducing news:hasAuthor, news:publishedBy, and news:occursInLocation. The LLM proposed merging GovernmentBody and ParliamentaryBody and reusing schema:Event directly; both were rejected because they would have broken the queries distinguishing parliamentary from government events. Keeping the hierarchy and rerunning confirmed the alignment held.

Used for: docs/mapping_specification.md, src/build_ontology.py


P03: Completion Analysis
Technique: zero-shot structured analysis

Prompt:
Analyse the current KG prototype. Identify at least 5 incomplete ontology elements and 5 incomplete instance elements; for each explain why it is incomplete, how it affects CQ coverage, and what retrieval could help. Propose a RAG completion workflow constrained to the ontology vocabulary.

Justification: identifying incompleteness across the ontology, instance graph, and CQs was impractical manually; the structured prompt produced a concrete gap list rather than a vague inventory.

Output: a gap list covering missing actor, department, and topic links. The LLM proposed using full article text as retrieval context; we replaced this with SPARQL neighbourhood queries because they were cheaper and kept proposals tied to the existing graph structure. That decision drove the retrieve-verbalise-prompt-validate design in complete_kg.py.

Used for: docs/completion_analysis.md, src/complete_kg.py


P04: LLM-Assisted Entity and Event Extraction
Technique: zero-shot with structured output schema

Prompt:
You are an information extraction assistant for a knowledge graph about UK parliamentary and government policy events. Use only evidence from the supplied article. Do not invent entities or events. Return only ontology-aligned JSON.

Runtime input: article metadata, content, and heuristic output. Required output: entity fields and an events list with per-event actor, topic, and body scoping.

Justification: heuristics alone could not reliably classify event types or distinguish politicians from mentioned organisations; the structured schema kept every output field tied to the ontology vocabulary.

Output: structured JSON cached per article ID, converted by json_to_rdf.py. Early runs had actor extraction too broad; adding "use only evidence from the supplied article" tightened precision. Party names still appeared occasionally, requiring a code-level blocklist.

Used for: src/data_extraction.py, src/openai_client.py


P05: LLM-Assisted KG Completion
Technique: zero-shot with closed-vocabulary constraint

Prompt:
Given a policy event and retrieved context, propose missing property values from the declared vocabulary only. proposed_actors: named individual politicians only, not parties, departments, or roles. proposed_departments: named UK government departments or official bodies. proposed_topics must come from this list: Defence, Economic Policy, Education, Energy, Government Policy, Healthcare, Housing, Immigration, Parliament, Public Spending, Taxation. Return only JSON.

Runtime input: verbalised event description plus up to three article headlines and source titles from the event's KG neighbourhood.

Justification: completing missing links from training knowledge alone produces hallucinated or out-of-vocabulary values; grounding in retrieved context tied proposals to evidence already in the dataset.

Output: proposed triples cached per event URI, validated against a blocklist and context overlap check before writing. Party names were entering the involvesActor relation in early iterations; restricting proposed_actors to named politicians fixed this. Constraining topics to a closed enum eliminated hallucinated names.

Used for: src/complete_kg.py


P06: OWL2 Class and Property Generation
Technique: few-shot

Prompt 1 (initial): Generate valid Turtle (prefix news: <http://example.org/news#>) for these classes with subclass parents: [class list including NewsArticle, PolicyEvent, OfficialBody hierarchy]. Object properties with domain/range: [property list including hasAuthor, involvesActor, issuedByDepartment].

Prompt 2 (few-shot correction):
The output has problems. Use this exact format:

news:NewsArticle a owl:Class ;
    rdfs:subClassOf schema:NewsArticle ;
    rdfs:label "News Article" .

Regenerate all classes and properties from the list using this pattern.

Justification: the LLM produced a first draft the team could validate rather than authoring every triple by hand.

Output: draft Turtle used as a starting point; the final ontology was refactored into build_ontology.py with hierarchy refinements added manually. The few-shot correction was needed because the initial output used inconsistent Turtle patterns. Domain and range values for reportedByArticle and representedInOfficialSource were wrong in every run and needed manual correction.

Used for: ontology/news_ontology.ttl


P07: SPARQL Query Generation
Technique: iterative prompting

Prompt 1: Here are our 20 CQs and Turtle ontology [pasted]. Write a SPARQL 1.1 SELECT query for each using PREFIX news: <http://example.org/news#>, PREFIX schema: <https://schema.org/>.

Prompt 2 (fix): CQ06, CQ09, and CQ20 return empty results or wrong structure. Here are sample triples from the actual graph [pasted]. Rewrite those three queries to match.

Justification: writing 20 SPARQL queries from scratch would have taken significant time; the LLM draft covered most usably and concentrated manual effort on cases where graph shape differed from what the model assumed.

Output: 20 queries in news_competency_queries.rq, tested against the completed KG. Several were rewritten because the LLM generated article-centric patterns and assumed outdated property names.

Used for: queries/news_competency_queries.rq


Reflection

LLMs were most reliable when the output format was tightly constrained: generating a Turtle draft (P06), producing SPARQL skeletons (P07), and structuring a gap list from a known schema (P03). The knowledge acquisition bottleneck shifted from authoring to auditing, but did not disappear.

In P06 domain and range pairs were wrong across multiple runs; the fix was to supply a concrete example and regenerate rather than correct in place. In P04 and P05 party names entered fields restricted to individual politicians, reflecting the open-world assumption LLMs operate under: without explicit enumeration they treat any plausible value as valid, so ABox population always needs a secondary check. A grounding constraint fixed P04; a closed-vocabulary enum fixed P05. In P02 the model proposed structurally valid but domain-inappropriate class merges; TBox decisions consistently needed human override regardless of how well the prompt was structured.

Hierarchy design, property characteristic choices, and the ontology-level versus instance-level gap distinction all required human judgment. Treating generated output as a draft to audit was the only approach that worked.
