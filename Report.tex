\section{Introduction}\label{sec:introduction}
%------------------------------------------------------------------

This project builds an automated knowledge graph (KG) for UK parliamentary and
government policy events reported in UK news between 6 March 2026 and 6 April
2026. The pipeline collects Guardian articles, UK Parliament written statements,
GOV.UK policy records, and optional Wikidata enrichment data; maps them into RDF;
builds an event-centred ontology; enriches the merged graph with source-linking
completion; and executes 20 SPARQL competency queries over the completed KG.

\subsection{Team Roles}

The repository follows the coursework team-role model.

\begin{itemize}[leftmargin=*,nosep]
    \item \textbf{Domain expert/client:} Abdrakhman Salmenov set the project scope,
    made domain decisions, and kept documentation coherent.
    \item \textbf{Modelling experts:} Aditya Ranjan and Kasim Morsel designed the
    ontology, mappings, queries, prompts, and evaluation methodology.
    \item \textbf{Requirements, data ingestion, and LLM pipeline:} Yingtao Zheng
    and Immanuel Fradinho Oliveira worked on data sources, access code, data
    preparation, LLM extraction support, and pipeline automation.
\end{itemize}

\subsection{Technology Stack}

\begin{itemize}[leftmargin=*,nosep]
    \item \textbf{Programming language:} Python.
    \item \textbf{Knowledge graph stack:} RDF, Turtle, SPARQL, and \code{rdflib}.
    \item \textbf{Sources:} Guardian API, UK Parliament written-statements API,
    GOV.UK Search API, and optional Wikidata SPARQL enrichment.
    \item \textbf{LLM integration:} OpenAI structured extraction support with
    schema validation and local caching.
    \item \textbf{Testing:} \code{pytest} tests for ontology construction,
    normalisation, RDF generation, completion, and query execution.
\end{itemize}

%------------------------------------------------------------------
\section{Data Sources}\label{sec:data_sources}
%------------------------------------------------------------------

The coursework requires both textual and structured data. The final pipeline uses
Guardian as the main textual reporting source, Parliament and GOV.UK as official
source-record providers, and Wikidata as optional structured enrichment.

\begin{itemize}[leftmargin=*,nosep]
    \item \textbf{Guardian API:} provides article headlines, URLs, dates, bylines,
    summaries, tags, and full body text. The body text supports extraction of
    policy events, actors, institutions, topics, and locations.
    \item \textbf{UK Parliament written-statements API:} provides official
    parliamentary source records used to ground parliamentary and ministerial
    events.
    \item \textbf{GOV.UK Search API:} provides official government policy,
    announcement, guidance, consultation, speech, and press-release records.
    \item \textbf{Wikidata SPARQL endpoint:} provides structured background data
    for politicians, political parties, and government bodies.
\end{itemize}

The latest validated live run collected 253 Guardian records, 20 Parliament
records, 459 GOV.UK records, and Wikidata enrichment for 1730 politicians, 968
parties, and 490 government bodies. Raw snapshots are saved under
\filepath{data/raw/}, allowing cached reruns.

\section{Ontology Design}\label{sec:ontology_design}
%------------------------------------------------------------------

The ontology is generated programmatically by \filepath{src/build_ontology.py}
and written to \filepath{ontology/news_ontology.ttl}. It reuses Schema.org and
BBC Core Concepts while adding a local \code{news:} namespace for the coursework
domain.

\begin{table}[t]
\centering
\caption{Core ontology terms in the implemented event-centred model.}
\label{tab:ontology}
\setlength{\tabcolsep}{5pt}
\begin{tabular}{@{}p{2.7cm}p{9.3cm}@{}}
\toprule
\textbf{Layer} & \textbf{Implemented terms} \\
\midrule
Events & \ns{PolicyEvent}, \ns{ParliamentaryEvent}, \ns{GovernmentPolicyEvent}, \ns{ParliamentaryDebate}, \ns{MinisterialStatement} \\
Actors and institutions & \ns{PoliticalActor}, \ns{PoliticalParty}, \ns{OfficialBody}, \ns{GovernmentBody}, \ns{GovernmentDepartment}, \ns{ParliamentaryBody} \\
Topics and places & \ns{PolicyTopic}, \ns{Location} \\
Reporting and provenance & \ns{NewsArticle}, \ns{NewsOrganisation}, \ns{Journalist}, \ns{SourceRecord}, \ns{OfficialSourceRecord}, \ns{ParliamentSourceRecord}, \ns{GovernmentSourceRecord} \\
\bottomrule
\end{tabular}
\end{table}

The ontology satisfies the extension requirement through multiple subclasses and
subproperties. For example, \ns{PolicyEvent} extends BBC Core Concepts
\code{core:Event}, \ns{Location} extends \code{core:Place}, \ns{NewsArticle}
extends \code{schema:NewsArticle}, and \ns{OfficialBody} extends
\code{schema:Organization}. Properties such as \ns{concernsPolicyTopic},
\ns{occursInLocation}, \ns{publishedBy}, \ns{hasAuthor}, \ns{publishedDate}, and
\ns{articleURL} are aligned with Schema.org or BBC Core Concepts properties.

The defended core ontology is deliberately event-centred. Older article-analytics
terms such as sentiment, article subtype, and follow-up links are not part of the
current core TBox.

\section{Pipeline and Mappings}\label{sec:pipeline}
%------------------------------------------------------------------

The pipeline is orchestrated by \filepath{src/main.py}. It can run against live
APIs or cached snapshots. The main command is:

\begin{verbatim}
python -m src.main
\end{verbatim}

The cached mode is:

\begin{verbatim}
python -m src.main --from-cache
\end{verbatim}

The mapping layer converts normalised records into articles, source records,
policy events, topics, actors, institutions, and locations. Official Parliament
and GOV.UK records are typed as source records and can be linked to events through
\ns{representedInOfficialSource}. The completion stage then adds inverse
\ns{reportsOn} links and \ns{matchedToSourceRecord} links for source integration.

\section{Competency Questions}\label{sec:cq}
%------------------------------------------------------------------

The project defines 20 competency questions in
\filepath{docs/competency_questions.md}. Ten were manually authored from the
domain requirements and ten were generated with LLM assistance before manual
revision. They are implemented as SPARQL queries in
\filepath{queries/news_competency_queries.rq}.

The questions deliberately exercise non-trivial ontology paths, including:

\begin{itemize}[leftmargin=*,nosep]
    \item event-to-topic retrieval;
    \item ministerial-statement-to-department links;
    \item actor, party, and topic aggregation;
    \item official-source representation and source-system provenance;
    \item publisher and journalist paths through articles to events;
    \item diagnostic missing-link queries for completion analysis.
\end{itemize}

The completion stage added 504 triples to the prototype graph: 266 inverse
\ns{reportsOn} links and 238 \ns{matchedToSourceRecord} links. This is most visible
in source-integration audits, while CQ11 and CQ12 use official source
representation to test institution and topic coverage.

The main strengths are source traceability, event-to-topic links, institution-event
links, and the ability to query across article, event, and official-source layers.
The main weaknesses are event canonicalisation, incomplete actor disambiguation,
and limited evidence metadata for completion-generated links.

\section{Testing and Reproducibility}\label{sec:testing}
%------------------------------------------------------------------

Automated tests are stored under \filepath{tests/}. They cover ontology
construction, RDF generation, completion, and query execution. The expected test
command is:

\begin{verbatim}
python -m pytest
\end{verbatim}

Reproducibility is supported through saved raw snapshots, timestamped processed
JSON outputs, generated Turtle graphs, and timestamped query results. The pipeline
also supports cached source runs with \code{--from-cache}.

%------------------------------------------------------------------
\section{AI Usage and Future Work}\label{sec:ai_usage}
%------------------------------------------------------------------

OpenAI is used in a constrained supportive role for extraction augmentation and
evaluation baselines. Runtime outputs are validated against structured formats and
can be cached locally. AI-generated coursework artefacts, such as competency
questions and prompts, were manually reviewed before being encoded into the final
ontology, queries, and documentation.

The current completion stage is deterministic graph enrichment, not a full
retrieval-augmented generation system. Future work may add a RAG layer that
retrieves article and official-source evidence before proposing ontology-compatible
triples. Such a layer should keep the same validation discipline: retrieve
evidence, generate candidate triples, validate against the ontology, then merge
only accepted assertions with provenance.

%------------------------------------------------------------------
\section{Conclusion}\label{sec:conclusion}
%------------------------------------------------------------------

The repository delivers a working automated KG pipeline for UK parliamentary and
government policy events. The current implementation collects live data, builds a
programmatic ontology, maps textual and official source records to RDF, enriches
the graph with source-integration links, and answers all 20 competency questions.
The strongest final claim is that the system is reproducible, ontology-aligned,
and queryable, with clear remaining work around entity resolution, event
canonicalisation, and richer provenance for completion links.
