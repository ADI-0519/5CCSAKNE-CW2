\section{Introduction}\label{sec:introduction}
%------------------------------------------------------------------

This project builds an automated knowledge graph (KG) pipeline for UK politics and
policy news (6 March--6 April 2026). The pipeline collects articles from the Guardian
API and NewsAPI, queries the Wikidata SPARQL endpoint for structured UK political
entity data, extracts entities and events from article text, maps both source types to
RDF, enriches the graph through a completion stage, and runs 20 SPARQL competency
queries.

\textbf{Tech stack:} Python, \code{rdflib}, OpenAI GPT-4o-mini (structured JSON
outputs with local caching), \code{pytest}.

\textbf{Roles:} Abdrakhman Salmenov (domain expert); Aditya Ranjan and Kasim Morsel
(modelling experts); Yingtao Zheng and Immanuel Fradinho Oliveira (data ingestion and
LLM pipeline).

\textbf{Deviations:} NewsAPI developer-tier access returned only 100 results (3 retained
articles), so Wikidata was added as the primary structured source. Legacy
technology-oriented keywords in \filepath{src/config.py} were retained for pipeline
compatibility while the final domain was fixed as UK politics and policy.

%------------------------------------------------------------------
\section{Data Source Selection}\label{sec:data_sources}
%------------------------------------------------------------------

The coursework requires at least one textual and one structured source.

\begin{itemize}[leftmargin=*,nosep]
    \item \textbf{Guardian API (textual):} full \code{bodyText} content for NLP
    extraction. 255 articles retained. Implemented in \filepath{src/data\_collection.py}.
    \item \textbf{Wikidata SPARQL endpoint (structured):} typed entity records for UK
    politicians ($\sim$5,600), political parties ($\sim$960), and government bodies
    ($\sim$150), mapped directly to RDF without NLP. Implemented in
    \filepath{src/wikidata\_collection.py}.
    \item \textbf{NewsAPI (supplementary):} structured article metadata from UK
    publishers; 3 articles retained after scope filtering.
\end{itemize}

The Guardian was chosen for its full body text enabling genuine extraction. Wikidata
was chosen for its public SPARQL endpoint and typed political actor data requiring no
API key. Source selection prompts are logged in \filepath{prompts/prompts.txt}.

\section{Extension of Existing Ontologies}\label{sec:ontology_design}
%------------------------------------------------------------------

The ontology is built programmatically in \filepath{src/build\_ontology.py} and
serialised to \filepath{ontology/news\_ontology.ttl}. It extends \textbf{Schema.org}
(articles, people, organisations, metadata) and the \textbf{BBC Core Concepts Ontology}
(events, places) under the \code{news:} namespace.

\section{Competency Questions}\label{sec:cq}
%------------------------------------------------------------------

Twenty competency questions were defined: 10 elicited manually from domain requirements
(covering journalists, publishers, person and party mentions, sentiment, topics, word
counts, updated articles, and follow-up links) and 10 generated with LLM assistance
and then revised manually for relevance and non-duplication. The prompt for CQ
augmentation is documented in \filepath{prompts/prompts.txt}. All 20 are
operationalised by the SPARQL queries in \filepath{queries/news\_competency\_queries.rq}.

%------------------------------------------------------------------
\section{Mappings}\label{sec:mappings}
%------------------------------------------------------------------

The pipeline implements two separate mapping paths for textual and structured sources.

\textbf{Textual path (Guardian + NewsAPI):} \filepath{src/data\_extraction.py}
combines heuristic and optional OpenAI-assisted extraction. The heuristic layer
identifies people, organisations, and locations via controlled lists and regex;
topics via weighted keyword groups in \filepath{src/config.py}; article subtype
(\code{NewsArticle}, \code{OpinionArticle}, \code{BreakingNewsArticle}); sentiment
(\code{Positive}/\code{Negative}/\code{Neutral}); and event candidates. The OpenAI
layer uses strict JSON-schema outputs, validated before use and cached under
\filepath{data/cache/openai/}; the pipeline falls back to heuristics if OpenAI is
unavailable. Extracted records are converted to RDF by \filepath{src/json\_to\_rdf.py}.

\textbf{Structured path (Wikidata):} \filepath{src/wikidata\_to\_rdf.py} converts
SPARQL results to RDF by direct field-to-property mapping---name, party, constituency,
gender, date of birth, founding date, and headquarters map to specific ontology classes
and properties with no NLP.

\textbf{Completion:} \filepath{src/complete\_kg.py} enriches the merged prototype
graph, adding inferred sentiment, section labels, article subtypes, topics, word
counts, update timestamps, and editorial follow-up links (\ns{hasFollowUp}).

\section{KG Completion}\label{sec:completion}
%------------------------------------------------------------------

Five incomplete ontology elements were identified: sentiment typing, section labelling,
article subtype assignment, topic coverage, and event label specificity. Five incomplete
instance elements were identified: missing sentiment values, unlabelled article
sections, sparse topic assignments, generic event labels, and incomplete follow-up
links.

The completion strategy uses RAG: \filepath{src/complete\_kg.py} queries the prototype
graph and adds validated triples for each gap. The clearest measurable result is
\ns{hasFollowUp} coverage increasing from 14 links in the prototype KG to 90 links
in the completed KG. Sentiment and event values are maintained using constrained
vocabularies rather than free-form text, keeping graph consistency.

\section{Prompts}\label{sec:prompts}
%------------------------------------------------------------------

Eight prompts were versioned and logged in \filepath{prompts/prompts.txt}:
(1)~initial pipeline planning;
(2)~competency-question augmentation;
(3)~ontology review against reused vocabularies;
(4)~source-to-ontology mapping draft;
(5)~completion gap analysis;
(6)~evaluation methodology design;
(7)~runtime entity and event extraction;
(8)~runtime KG completion.
Prompts 1--6 were used during design and revised manually before encoding into
artefacts. Prompts 7--8 execute at runtime with strict JSON-schema validation before
outputs enter the graph.

\textbf{Quality:} All 20 competency queries return results. The KG is most reliable
for article metadata, publisher and author information, topic assignment, article
subtype, and sentiment---fields mapped from source metadata or validated against
constrained vocabularies. Weaker areas: person and organisation extraction
over-generates via regex; event labels remain generic; follow-up links are editorial
heuristics; the corpus is Guardian-dominated.

\textbf{Performance and reproducibility:} the pipeline runs end to end from live APIs
or cached snapshots and reuses cached OpenAI responses for deterministic offline reruns.
The \code{pytest} suite covers ontology construction, extraction, normalisation, RDF
conversion, completion, and query execution.

\textbf{KG vs.\ direct LLM:} KG-based answers are reproducible, auditable, and grounded
in structured triples. Direct LLM prompting is more fluent but non-deterministic and
non-traceable.

%------------------------------------------------------------------
\section{Conclusions}\label{sec:conclusions}
%------------------------------------------------------------------

The pipeline delivers a working, reproducible KG: all 20 competency queries return
results, the ontology correctly extends two existing vocabularies, and separate mapping
paths handle textual and structured sources. Remaining weaknesses are entity precision,
generic event labels, and source imbalance. The repository structure---\filepath{src/},
\filepath{ontology/}, \filepath{queries/}, \filepath{prompts/}, \filepath{docs/},
\filepath{tests/}---keeps code, artefacts, and evaluation evidence versioned together.
