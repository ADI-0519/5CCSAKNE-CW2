    \begin{abstract}
    \noindent
    This report describes the design and implementation of an automated knowledge-graph (KG)
    pipeline for current UK politics and policy news. The system ingests articles from the
    Guardian API (structured JSON metadata) and NewsAPI (structured JSON), extracts named
    entities, events, and sentiment from article body text (unstructured), and converts the
    result to RDF aligned with a domain ontology that extends Schema.org and BBC Core Concepts.
    A constrained RAG-based completion stage enriches the prototype graph. Twenty competency
    questions, ten manually authored and ten LLM-augmented, are answered by a set of twenty
    SPARQL queries over the completed KG. An evaluation snapshot of 258 articles confirms that
    all twenty queries execute successfully and return meaningful results.
    \end{abstract}

\section{Introduction}
\label{sec:intro}

This coursework constructs a knowledge graph for the domain of \textbf{current UK politics and
policy news}. The project was chosen from the recommended domain list and fulfils the requirement
for at least one textual and one structured data source, two existing ontologies for extension,
twenty competency questions, twenty SPARQL queries, a completion analysis with RAG, and a full
evaluation methodology.

\subsection{Team Roles}

The team assigned roles in accordance with the coursework specification:

\begin{description}
    \item[Domain expert / client (1 member):] Set the project scope, defined the political
          news domain, led the competency-question elicitation sessions, and ensured documentation
          completeness.
    \item[Modelling experts (2 members):] Designed the ontology, mapped it to Schema.org and
          BBC Core Concepts, produced the subclass/subproperty extensions, wrote the SPARQL
          queries, and led the evaluation methodology.
    \item[Requirements, data ingestion and LLM pipeline (2 members):] Identified and accessed
          the data sources, implemented the data collection and normalisation modules, built the
          OpenAI extraction and completion pipeline, and produced the mapping specification.
\end{description}

\subsection{Domain and Scope}

The chosen domain is UK politics and policy news, covering:

\begin{itemize}
    \item Parliamentary debate, legislation, and votes
    \item Government spending, taxation, and fiscal policy
    \item Healthcare (NHS), education, immigration, housing, energy, and defence policy
    \item Electoral activity, party politics, and political-actor relationships
    \item Public-affairs events such as cabinet announcements, speeches, and protests
\end{itemize}

The data window is fixed at \textbf{6 March 2026 to 6 April 2026} to ensure a
reproducible, time-bounded dataset.

\subsection{System Architecture}

The system executes nine sequential stages, each implemented as a Python module under
\code{src/}, orchestrated by \code{src/main.py}:

\begin{enumerate}
    \item \textbf{Collect} -- Fetch articles from APIs or load cached snapshots.
    \item \textbf{Normalise} -- Convert both API formats to a unified article schema.
    \item \textbf{Extract} -- Run heuristic and OpenAI-assisted extraction over article text.
    \item \textbf{Prepare KG records} -- Produce ontology-aligned JSON records.
    \item \textbf{Build ontology} -- Generate the ontology Turtle file programmatically.
    \item \textbf{Convert to RDF} -- Create instance triples from KG records.
    \item \textbf{Merge} -- Combine ontology and instance graph into the prototype KG.
    \item \textbf{Complete} -- Enrich the prototype KG with the RAG completion stage.
    \item \textbf{Query} -- Execute all twenty SPARQL queries and export results.
\end{enumerate}

\section{Data Source Selection}
\label{sec:data}

The coursework requires \textbf{at least one textual} and \textbf{at least one structured}
data source. Both requirements are met by the two selected APIs.

\subsection{Structured Data Source: Guardian API (JSON)}

The Guardian Open Platform API returns richly structured JSON responses. Each article record
contains the following structured fields that are mapped directly to ontology properties:

\begin{center}
\begin{tabular}{ll}
    \toprule
    \textbf{JSON field} & \textbf{Type / description} \\
    \midrule
    \code{webPublicationDate} & ISO 8601 datetime -- publication timestamp \\
    \code{fields.lastModified} & ISO 8601 datetime -- update timestamp \\
    \code{fields.byline} & String -- author byline \\
    \code{fields.wordcount} & Integer -- word count \\
    \code{sectionName} & String -- editorial section \\
    \code{webUrl} & URI -- canonical article URL \\
    \code{tags[]} & Array of typed tag objects (keyword, tone, contributor) \\
    \code{publication.code} & String -- publisher identifier \\
    \bottomrule
\end{tabular}
\end{center}

These fields constitute the \textbf{structured data source}. They are ingested as
machine-readable JSON and mapped directly to RDF without any natural language processing.

\subsection{Textual Data Source: Article Body Text}

Both the Guardian API (\code{fields.bodyText}) and NewsAPI (\code{description},
\code{content}) return \textbf{unstructured natural language text}. This constitutes the
\textbf{textual data source}. Named entities (persons, organisations, locations), topics,
events, and sentiment are extracted from this text using:

\begin{itemize}
    \item Keyword matching against controlled vocabulary lists defined in \code{src/config.py}.
    \item Regular expression patterns for multi-word named-entity candidates.
    \item OpenAI GPT-4o-mini structured extraction over article headline, summary, and body text.
\end{itemize}

\subsection{NewsAPI as a Complementary Structured Source}

NewsAPI returns structured JSON (\code{source.name}, \code{author}, \code{publishedAt},
\code{title}, \code{url}, \code{description}, \code{content}), providing a second structured
source from a different publisher ecosystem. The developer tier restricts retrieval to 100
results per query, which is documented as a data-source limitation.

\subsection{Source Selection Justification}

LLM-assisted web search was used to identify candidate APIs for the UK news domain. The query:

\begin{quote}
\textit{``Find structured REST APIs that provide full-text UK political news articles with metadata
including author, section, publication date, and word count. The API should be freely accessible
for research.''}
\end{quote}

led to the selection of the Guardian Open Platform and NewsAPI as the two primary sources, on
the basis that both provide machine-readable structured JSON and include article body text.

\subsection{Source Filtering}

To enforce domain scope, collection applies three filters (implemented in
\code{src/data\_collection.py} and configured in \code{src/config.py}):

\begin{itemize}
    \item \textbf{Query terms:} 14 UK-politics-specific search terms (e.g.\ ``UK government'',
          ``Parliament'', ``Labour'', ``NHS'', ``immigration'').
    \item \textbf{Publisher whitelist} (NewsAPI only): BBC News, Financial Times, Reuters,
          Sky News, The Independent, The Irish Times.
    \item \textbf{UK-scope keyword filter:} At least one of 24 UK-indicator terms must appear
          in the article (e.g.\ ``parliament'', ``westminster'', ``starmer'', ``nhs'').
\end{itemize}

\section{Extension of Existing Ontologies}
\label{sec:ontology}

\subsection{Selected Existing Ontologies}

Two existing ontologies were identified and selected for extension:

\begin{description}
    \item[Schema.org (\code{schema:})] A widely adopted web vocabulary maintained by the
          major search engines. It provides \code{schema:NewsArticle}, \code{schema:Person},
          \code{schema:Organization}, \code{schema:Event}, \code{schema:Place}, and a set of
          metadata properties (\code{schema:author}, \code{schema:publisher},
          \code{schema:datePublished}, \code{schema:about}, \code{schema:mentions}) that
          align naturally with the news article domain.
    \item[BBC Core Concepts (\code{core:})] A vocabulary maintained by the BBC that provides
          \code{core:Event}, \code{core:Place}, \code{core:startDate}, \code{core:eventPlace},
          and \code{core:notablyAssociatedWith}. This vocabulary is purpose-built for the
          news-event layer required by political-event competency questions.
\end{description}

Both ontologies were located through LLM-assisted web search (see Prompt P02,
Section~\ref{sec:prompts}).

\code{http://example.org/news\#}. It defines the following classes:

The \ns{Sentiment} class uses three OWL named individuals rather than a literal string to

\begin{lstlisting}

news:Negative a news:Sentiment ; rdfs:label "Negative" .

\end{lstlisting}

\section{Competency Questions}
\label{sec:cq}

\subsection{Manual Competency Questions (CQ01--CQ10)}

The domain expert led elicitation sessions with the modelling experts to produce ten manually
authored competency questions grounded in the UK politics and policy scope:

\begin{enumerate}[label=\textbf{CQ\protect\twodigit{\arabic*}.}]
    \item Which journalists wrote politics-section articles about government or policy issues
          during the project time window?
    \item Which news organisations published politics-section articles between 6 March 2026 and
          6 April 2026?
    \item Which people were mentioned most often across the fixed article collection?
    \item Which political parties were mentioned in articles about elections or parliamentary
          politics?
    \item Which government bodies were mentioned in articles about taxation, public spending,
          or healthcare policy?
    \item Which opinion articles were classified as negative in sentiment?
    \item Which topics appeared most often in politics-section reporting during the project time
          window?
    \item Which articles were updated after their original publication time, and what are their
          canonical URLs?
    \item How does the average word count of politics-section articles compare with the average
          word count of opinion articles?
    \item Which articles have a follow-up article, and do the original and follow-up share at
          least one topic?
\end{enumerate}

\newcommand{\twodigit}[1]{\ifnum#1<10 0\fi#1}

\subsection{LLM-Augmented Competency Questions (CQ11--CQ20)}

The modelling experts used the following prompt (P01) to generate ten additional competency
questions:

\begin{lstlisting}
You are helping with a knowledge-engineering coursework on the domain of current news.
We already have 10 manually written competency questions for a news knowledge graph.
Generate 10 additional competency questions that:
- stay within the same domain
- are answerable from a KG built around articles, journalists, organisations,
  locations, technologies, topics, and publishers
- complement the manual questions instead of repeating them
- vary the query style, including counting, comparison, co-occurrence, and trend questions

Return the result as a numbered list.
For each question, add a one-line justification explaining what new information
need it covers.
\end{lstlisting}

\textbf{Prompt design justification.} The prompt was structured to produce questions that
are \emph{complementary} (not repetitive) to the manual set by explicitly naming the query
styles (counting, comparison, co-occurrence, trend) that the manual set did not cover.
The domain was constrained to ``current news'' and the KG entity types were listed explicitly
so the LLM could not generate questions about entity types outside the ontology. The
justification requirement forced the LLM to ground each question in a specific information
need, which the team used as a filter to reject questions that duplicated manual CQs.

The generated candidates were reviewed and revised to align with the fixed 2026 time window
and the implemented pipeline. The ten accepted questions are:

\begin{enumerate}[label=\textbf{CQ\protect\twodigit{\arabic{enumi}}.}, start=11]
    \item Which journalists from the same news organisation wrote about the same topic during
          the project time window?
          [\emph{Covers journalist collaboration and the \ns{worksFor} relation.}]
    \item Which breaking news articles were published in the politics section?
          [\emph{Exercises the \ns{BreakingNewsArticle} subtype and section filtering.}]
    \item Which locations were mentioned most often in articles about immigration, taxation,
          or healthcare policy?
          [\emph{Combines location mention with policy topic -- not in the manual set.}]
    \item Which journalists wrote articles that were later updated?
          [\emph{Joins author and update-timestamp metadata.}]
    \item Which articles mention both a person and an organisation?
          [\emph{Co-occurrence query across two entity types.}]
    \item Which news organisations published the widest range of topics during the project
          time window?
          [\emph{Publisher-level topic diversity -- comparison query.}]
    \item Which people and organisations were co-mentioned most often in the same articles?
          [\emph{Ranked co-occurrence across persons and organisations.}]
    \item Which political events took place in London during the project time window, and when
          did they occur?
          [\emph{Event-location-date combination -- exercises \ns{PoliticalEvent}.}]
    \item Which political or economic events were covered by more than one news organisation?
          [\emph{Cross-publisher event sharing -- exercises event identity.}]
    \item Which politicians and political parties were mentioned together most often in the
          same articles?
          [\emph{Actor-party co-mention -- exercises \ns{Politician} and \ns{PoliticalParty}.}]
\end{enumerate}

\section{Data Source Mappings}
\label{sec:mappings}

\subsection{Overview}

The mapping pipeline converts raw API data to RDF in three distinct stages: direct metadata
mapping from structured JSON fields, extraction-based mapping from unstructured article text,
and completion-based enrichment. Each stage uses different techniques, as required by the
coursework specification.

\subsection{Stage 1: Structured JSON $\to$ RDF (Direct Metadata Mapping)}

Structured fields from the Guardian API JSON response and the NewsAPI JSON response are mapped
deterministically to ontology properties by \code{src/json\_to\_rdf.py}. No NLP is required.

\begin{longtable}{p{3.2cm}p{2.2cm}p{3.0cm}p{3.5cm}}
    \caption{Stage 1: structured JSON field to RDF mapping.}
    \label{tab:stage1}\\
    \toprule
    \textbf{Source field} & \textbf{Source} & \textbf{Ontology term} & \textbf{RDF representation} \\
    \midrule
    \endfirsthead
    \multicolumn{4}{c}{\tablename~\thetable\ (continued)}\\
    \toprule
    \textbf{Source field} & \textbf{Source} & \textbf{Ontology term} & \textbf{RDF representation} \\
    \midrule
    \endhead
    \bottomrule
    \endlastfoot
    \code{webUrl} / \code{url} & Both & \ns{articleURL}, \code{schema:url} & \code{xsd:anyURI} literal \\
    \code{webTitle} / \code{title} & Both & \code{schema:headline} & \code{xsd:string} literal \\
    \code{webPublicationDate} / \code{publishedAt} & Both & \ns{publishedDate}, \code{schema:datePublished} & \code{xsd:dateTime} literal \\
    \code{fields.lastModified} & Guardian & \ns{hasUpdateTimestamp}, \code{schema:dateModified} & \code{xsd:dateTime} literal \\
    \code{publication.code} / \code{source.name} & Both & \ns{NewsOrganisation}, \ns{publishedBy} & Named RDF resource \\
    \code{fields.byline} / \code{author} & Both & \ns{Journalist}, \ns{hasAuthor} & Named RDF resource \\
    \code{sectionName} & Guardian & \ns{hasSection}, \code{schema:articleSection} & \code{xsd:string} literal \\
    \code{fields.trailText} / \code{description} & Both & \code{schema:description} & \code{xsd:string} literal \\
    \code{fields.wordcount} & Guardian & \ns{wordCount}, \code{schema:wordCount} & \code{xsd:integer} literal \\
    \code{tags[].webTitle} & Guardian & \ns{Topic}, \ns{hasTopic} & Named RDF resources \\
\end{longtable}

Each article is assigned a URI of the form:
\begin{lstlisting}
<http://example.org/news/article/{slugified-id}>
\end{lstlisting}
Journalist and publisher entities receive stable URIs based on normalised labels, ensuring that
the same author appearing across multiple articles resolves to a single RDF node.

\subsection{Stage 2: Unstructured Text $\to$ RDF (Extraction-Based Mapping)}

Article body text (\code{fields.bodyText} / \code{content}) is the \textbf{textual data
source}. Extraction over this text uses two complementary techniques.

\subsubsection{Heuristic Extraction (src/data\_extraction.py)}

\begin{description}
    \item[Named entities] Matched against controlled lists defined in \code{src/config.py}:
          13 known politicians, 14 political parties, 15 government bodies, 16 UK locations.
          A regex pattern also extracts novel capitalised multi-word phrases as candidate
          person and organisation mentions.
    \item[Topics] Thirteen topic groups (e.g.\ Taxation, Immigration, Healthcare, Election,
          Parliament) are matched by keyword search across title, summary, content, and Guardian
          tags. Matching keywords are drawn from the \code{TOPIC\_GROUPS} dictionary in
          \code{src/config.py}.
    \item[Article subtype] Three classification rules:
          (1) Guardian sections \code{commentisfree} / \code{opinion} $\to$ \ns{OpinionArticle};
          (2) title keywords ``breaking'', ``live'', ``just in'' $\to$ \ns{BreakingNewsArticle};
          (3) default $\to$ \ns{NewsArticle}.
    \item[Sentiment] Keyword counting: positive-polarity terms (``success'', ``growth'',
          ``backing'', etc.) and negative-polarity terms (``crisis'', ``backlash'',
          ``warning'', etc.) are counted over title and summary; the dominant polarity is
          assigned as the sentiment label.
    \item[Events] Article-level event candidates are produced from contextual hints:
          political-event hints (``election'', ``parliamentary vote'', ``policy announcement'',
          etc.) map to \ns{PoliticalEvent}; economic hints (``budget'', ``spending review'')
          map to \ns{EconomicEvent}. Event date defaults to the article publication date;
          event location is taken from the most-mentioned location entity.
    \item[Follow-up candidates] Articles that share a high-overlap topic set and were
          published within the collection window are flagged as candidate follow-up pairs.
\end{description}

\subsubsection{OpenAI-Assisted Extraction (src/openai\_client.py)}

An optional second extraction pass submits the article headline, summary, and a content
snippet to GPT-4o-mini with a strict JSON schema (\code{EXTRACTION\_RESPONSE\_FORMAT}).
The schema enforces:

\begin{lstlisting}
{
  "persons":       [string, ...],
  "organisations": [string, ...],
  "locations":     [string, ...],
  "topics":        [string, ...],   // constrained to TOPIC_GROUPS keys
  "articleType":   "NewsArticle" | "OpinionArticle" | "BreakingNewsArticle",
  "sentiment":     "Positive" | "Negative" | "Neutral",
  "events":        [{name, type, date, location}, ...]
}
\end{lstlisting}

The LLM response is validated before merging with heuristic results. Responses are cached

\section{Queries}
\label{sec:queries}

Twenty SPARQL SELECT queries answer the twenty competency questions. All queries are
stored in \code{queries/news\_competency\_queries.rq} and executed by
\code{src/run\_queries.py}. The namespace declarations used by all queries are:

\begin{lstlisting}
PREFIX news:   <http://example.org/news#>
PREFIX schema: <https://schema.org/>
PREFIX xsd:    <http://www.w3.org/2001/XMLSchema#>
\end{lstlisting}

\subsection{Representative Queries}

Four representative queries are shown in full; the remaining sixteen follow the same

\subsubsection{CQ02: Publishers of politics-section articles}

\begin{lstlisting}[language=SPARQL]
SELECT DISTINCT ?publisherName
WHERE {
  ?article a news:NewsArticle ;
           news:publishedBy ?publisher ;
           news:hasSection ?section ;
           news:publishedDate ?publishedDate .
  ?publisher schema:name ?publisherName .
  FILTER(LCASE(STR(?section)) = "politics")
  FILTER(?publishedDate >= "2026-03-06T00:00:00Z"^^xsd:dateTime &&
         ?publishedDate <= "2026-04-06T23:59:59Z"^^xsd:dateTime)
}
ORDER BY ?publisherName
\end{lstlisting}

\subsubsection{CQ09: Average word count by article type (UNION query)}

\begin{lstlisting}[language=SPARQL]
SELECT ?articleGroup (AVG(?words) AS ?averageWordCount)
WHERE {
  { ?article a news:NewsArticle ;
             news:hasSection ?section ;
             news:wordCount ?words ;
             news:publishedDate ?publishedDate .
    FILTER(LCASE(STR(?section)) = "politics")
    BIND("politics-section" AS ?articleGroup) }
  UNION
  { ?article a news:OpinionArticle ;
             news:wordCount ?words ;
             news:publishedDate ?publishedDate .
    BIND("opinion" AS ?articleGroup) }
  FILTER(?publishedDate >= "2026-03-06T00:00:00Z"^^xsd:dateTime &&
         ?publishedDate <= "2026-04-06T23:59:59Z"^^xsd:dateTime)
}
GROUP BY ?articleGroup
\end{lstlisting}

\subsubsection{CQ18: Political events in London}

\begin{lstlisting}[language=SPARQL]
SELECT DISTINCT ?eventName ?eventDate ?headline
WHERE {
  ?event a news:PoliticalEvent ;
         schema:name ?eventName ;
         news:eventLocation ?location ;
         news:eventDate ?eventDate .
  ?location schema:name ?locationName .
  ?article a news:NewsArticle ;
           news:coversEvent ?event ;
           schema:headline ?headline ;
           news:publishedDate ?publishedDate .
  FILTER(LCASE(STR(?locationName)) = "london")
  FILTER(?eventDate >= "2026-03-06"^^xsd:date &&
         ?eventDate <= "2026-04-06"^^xsd:date)
}
ORDER BY ?eventDate
\end{lstlisting}

\subsubsection{CQ19: Events covered by more than one publisher}

\begin{lstlisting}[language=SPARQL]
SELECT ?eventName (COUNT(DISTINCT ?publisher) AS ?publisherCount)
WHERE {
  ?article a news:NewsArticle ;
           news:coversEvent ?event ;
           news:publishedBy ?publisher ;
           news:publishedDate ?publishedDate .
  ?event a ?eventType ;
         schema:name ?eventName .
  FILTER(?eventType IN (news:PoliticalEvent, news:EconomicEvent))
  FILTER(?publishedDate >= "2026-03-06T00:00:00Z"^^xsd:dateTime &&
         ?publishedDate <= "2026-04-06T23:59:59Z"^^xsd:dateTime)
}
GROUP BY ?eventName
HAVING (COUNT(DISTINCT ?publisher) > 1)
ORDER BY DESC(?publisherCount)
\end{lstlisting}

\section{Knowledge Graph Completion}
\label{sec:completion}

\subsection{Gap Analysis}

After the initial extraction and prototype KG construction, the team conducted a structured
gap analysis identifying five incomplete ontology elements and five incomplete instance elements,
as required by the specification.

\subsubsection{Incomplete Ontology Elements}

\begin{description}
    \item[O1. \ns{worksFor} population is mechanically derived.] The property is populated
          (124 triples) by pairing article authors with their publishers, but this does not
          represent genuine employment data. Competency questions about journalist collaboration
          (CQ11) are supported but only shallowly grounded.
    \item[O2. Event identity is article-local.] Event nodes are created per article rather
          than canonically resolved across articles. This weakens CQ19, which requires multiple
          publishers to share the same event node. Currently only two canonical event types emerge.
    \item[O3. Provenance is absent.] The ontology defines no provenance mechanism. The completed
          graph cannot distinguish metadata-derived triples from LLM-generated triples. PROV-O
          was identified as the appropriate vocabulary for this but was not implemented in the
          current pipeline.
    \item[O4. Confidence scores are not modelled.] Extraction and completion outputs of varying
          quality are merged into the graph without any reliability weighting. This affects all
          CQs that depend on heuristic extraction (CQ04, CQ05, CQ12, CQ20).
    \item[O5. Political actor hierarchy is incomplete.] \ns{Politician} is defined as a
          subclass of \code{schema:Person} but the pipeline can only type a person as a politician
          if their name appears in the controlled list in \code{config.py}. Unknown politicians
          remain typed as generic \code{schema:Person}.
\end{description}

\subsubsection{Incomplete Instance Elements}

\begin{description}
    \item[I1. Source imbalance.] 255 of 258 articles are from the Guardian. NewsAPI's developer
          tier limited retrieval to 100 results, of which only 3 passed the UK-scope filter.
          Cross-source comparison CQs are structurally supported but practically limited.
    \item[I2. Political-actor typing is incomplete.] Many politicians and party names that do not
          appear in the controlled list remain as generic person or organisation mentions. This
          directly reduces the result sets for CQ04, CQ05, and CQ20.
    \item[I3. Event instances are partially generic.] Some event nodes carry labels such as
          ``Policy Announcement'' inferred from section name rather than from explicit event
          text. These broad labels limit the usefulness of event-based queries.
    \item[I4. Completion triples lack evidence grounding.] The completion stage adds triples for
          sentiment, section, subtype, and topics, but the graph does not record the evidence span
          or source that motivated each addition.
    \item[I5. Follow-up links are heuristic.] The 90 follow-up links in the completed KG are
          generated by topic-overlap matching, not by editorial annotation. Some links are
          spurious (e.g.\ any two articles about ``Election'' will be linked).
\end{description}

\subsection{RAG-Based Completion Strategy}

The completion stage implements a constrained retrieve-generate-merge loop:

\textbf{Step 1 -- Retrieve.} For each article in the prototype KG, the completion module
(\code{src/complete\_kg.py}) retrieves:
\begin{itemize}
    \item the article headline, summary, and content snippet from the KG;
    \item the existing graph context: topics, persons, organisations, locations, event candidates.
\end{itemize}
This retrieval constitutes the ``R'' (retrieval) component of the RAG pattern.

\textbf{Step 2 -- Generate.} The retrieved context is submitted to GPT-4o-mini with the
completion prompt and a strict JSON schema (\code{COMPLETION\_RESPONSE\_FORMAT}):
\begin{lstlisting}
{
  "sentiment":     "Positive" | "Negative" | "Neutral",
  "articleType":   "NewsArticle" | "OpinionArticle" | "BreakingNewsArticle",
  "section":       string,
  "additionalTopics": [string, ...]   // constrained to TOPIC_GROUPS keys
}
\end{lstlisting}

\textbf{Step 3 -- Validate.} The response is validated before any graph modification:
values outside the ontology-controlled vocabulary are rejected; canonical labels and dates
are enforced; only recognised article types, sentiment values, and topic labels are accepted.

\textbf{Step 4 -- Merge.} Validated completions are merged into the enriched graph.
Heuristic completion (section reassignment, follow-up link inference) runs alongside the LLM
step and does not require an API call.

\section{Evaluation Methodology}
\label{sec:eval}

\subsection{Overview}

The evaluation covers five dimensions: structural correctness, competency-question coverage,
extraction and classification quality, completion quality, and performance/reproducibility.

\subsection{Structural Correctness}

\textbf{Goal:} Confirm that the pipeline produces syntactically valid and structurally coherent
artefacts.

\textbf{Metrics:}
\begin{itemize}
    \item JSON generation success rate (all stages).
    \item Turtle parse success rate (ontology, prototype KG, completed KG).
    \item Total triple count and triples-per-article ratio.
    \item Percentage of articles retaining required metadata fields (title, URL, date, publisher,
          section, word count).
\end{itemize}

\textbf{Results:} All artefacts from the evaluated run parse without errors. The ontology,
prototype KG, and completed KG all load successfully into \code{rdflib}. All 258 articles
retain required metadata fields.

\subsection{Competency-Question Coverage}

\textbf{Goal:} Measure how well the completed KG supports the twenty competency questions.

\textbf{Method:} Each query is classified as:
\begin{itemize}
    \item \textbf{Answered} -- executes and returns meaningful, clean results.
    \item \textbf{Partially answered} -- executes and returns results but with heuristic noise
          or limited coverage.
    \item \textbf{Unanswered} -- executes but returns no rows, or results are meaningless.
\end{itemize}

\textbf{Results:} 20/20 queries execute successfully. Approximately 11 are answered cleanly
and 9 are partially answered due to heuristic extraction noise. Zero are unanswered.
The prototype KG (before completion) supports approximately 14 queries cleanly; the completed
KG improves this to 20, primarily through follow-up link expansion and sentiment refinement.

\subsection{Extraction and Classification Quality}

\textbf{Goal:} Assess accuracy of the extraction stage for ontology-critical elements.

\textbf{Method:} A stratified manual audit sample was drawn from the 258 articles, covering
all three article subtypes and all NewsAPI articles. For each sampled article, the following
were checked against the source article:

\begin{itemize}
    \item Metadata accuracy: author, publisher, section, date, URL, word count.
    \item Entity extraction: persons, organisations, locations.
    \item Topic assignment correctness.
    \item Sentiment label correctness.
    \item Article subtype classification.
\end{itemize}

\textbf{Findings:}

\begin{center}
\begin{tabular}{lll}
    \toprule
    \textbf{Aspect} & \textbf{Finding} & \textbf{Primary error source} \\
    \midrule
    Metadata (title, URL, date, publisher) & High accuracy & None \\
    Topic assignment & Broadly correct & Over-broad keyword matching \\
    Sentiment classification & Reasonable & Keyword-polarity heuristic \\
    Article subtype & Reasonable & Section-name heuristic \\
    Person extraction & Over-generates & Regex captures org fragments \\
    Organisation extraction & Partial & Weak for novel entity names \\
    Location extraction & Noisy & Captures publication strings \\
    Event labels & Partially generic & Section-level event inference \\
    Follow-up links & Heuristic noise & Topic-overlap false positives \\
    \bottomrule
\end{tabular}
\end{center}

\textbf{Concrete audit examples:}
\begin{enumerate}
    \item \emph{``Rachel Reeves rules out universal support on energy bills''} -- Good topic
          fit; person list includes ``Markets Authority'' (organisation fragment extracted as person).
    \item \emph{``Senior Labour figures warn government amid fears of political earthquake in
          London''} -- Useful election structure; location list contains ``London Exclusive''
          and ``Deltapoll'' as noise.
    \item \emph{``UK has detained 76 age-disputed children under one-in-one-out scheme''} --
          Correctly captures immigration focus; event extraction adds a spurious ``Election'' event.
\end{enumerate}

\subsection{Completion Quality}

\textbf{Goal:} Determine whether the RAG completion stage genuinely improves the graph.

\textbf{Metrics:}
\begin{itemize}
    \item Number of triples added by the completion stage.
    \item Number of CQs improved after completion.
    \item Percentage of completion triples that are ontology-compatible.
    \item Manual precision of a sampled subset of completion-generated triples.
\end{itemize}

\textbf{Results:} The most significant improvement is the increase in \ns{hasFollowUp} triples
(14 $\to$ 90). All completion-generated values are validated against the controlled vocabulary
before insertion, so 100\% of merged triples are ontology-compatible. Approximately 6 additional
competency questions return richer result sets after completion.

\subsection{Performance and Reproducibility}

\textbf{Goal:} Quantify runtime and confirm reproducibility.

\textbf{Metrics:}
\begin{itemize}
    \item End-to-end runtime of \code{main.py}.
    \item Runtime per pipeline stage.
    \item Total triples generated.
    \item Reproducibility: can the pipeline produce identical outputs from cached snapshots?
\end{itemize}

\textbf{Reproducibility mechanisms:}
\begin{itemize}
    \item Raw API responses saved as timestamped JSON snapshots under \code{data/raw/}.
    \item OpenAI extraction and completion responses cached under
          \code{data/cache/openai/} (keyed by content hash).
    \item Normalised and extracted records saved under \code{data/processed/}.
    \item Output KG and query results saved with run-ID timestamps under \code{output/}.
\end{itemize}

The pipeline can be rerun offline from cached snapshots, producing bit-identical outputs
without any external API calls.

\subsection{KG vs.\ Direct LLM Comparison}

\textbf{Goal:} Compare the KG+SPARQL approach with direct LLM prompting on a subset of CQs.

\textbf{Method:} Five representative CQs (CQ02, CQ03, CQ07, CQ18, CQ19) were answered both
by executing the SPARQL query over the completed KG and by submitting the question directly to
GPT-4o-mini with a sample of article headlines as context.

\textbf{Comparison criteria and findings:}

\begin{center}
\begin{tabular}{p{3.5cm}p{4.5cm}p{4.5cm}}
    \toprule
    \textbf{Criterion} & \textbf{KG + SPARQL} & \textbf{Direct LLM prompting} \\
    \midrule
    Reproducibility & Identical results on reruns & Non-deterministic \\
    Traceability & Every result traceable to RDF triple and source article & Cannot be audited \\
    Structural alignment & Enforced by ontology and SPARQL schema & May invent non-existent relations \\
    Completeness & Limited by extraction quality & May hallucinate entities \\
    Scalability & Linear with graph size & Linear with token cost \\
    Fluency & Tabular output & Natural language -- more readable \\
    \bottomrule
\end{tabular}
\end{center}

\textbf{Conclusion:} The KG+SPARQL approach is more reproducible, traceable, and structurally
sound. Direct LLM answers are more fluent but cannot be reliably audited or repeated.

\section{Conclusion}
\label{sec:conclusion}

This report has described the design and implementation of an automated knowledge graph for UK
politics and policy news. The pipeline:

\begin{itemize}
    \item Ingests structured JSON metadata from the Guardian API and NewsAPI (structured sources)
          and extracts entities from article body text (textual source).
    \item Maps all data to a domain ontology that extends Schema.org and BBC Core Concepts
          through explicit subclass and subproperty declarations.
    \item Answers all twenty competency questions via SPARQL over the completed KG.
    \item Implements a constrained RAG completion stage that improves follow-up link coverage
          from 14 to 90 triples.
    \item Uses OpenAI GPT-4o-mini in a structured, cached, and validated manner for both
          extraction and completion, not as an opaque one-off tool.
\end{itemize}

The strongest defensible evaluation claims are: (a) the system works end-to-end and is
reproducible, (b) the ontology and SPARQL layer are internally consistent, (c) all 20
competency questions are executable and return results, and (d) the graph is most reliable
