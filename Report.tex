\section{Introduction}\label{sec:introduction}
%------------------------------------------------------------------

\subsection{Purpose of the Project}

This project builds an automated knowledge graph (KG) for current UK politics and
policy news. The pipeline collects articles from the Guardian API and NewsAPI for
the fixed window 6 March 2026 to 6 April 2026, queries the Wikidata SPARQL
endpoint for structured entity data on UK politicians, political parties, and
government bodies, extracts entities and events from article text, maps both
textual and structured sources into RDF, enriches the prototype graph with a
completion stage, and executes 20 SPARQL competency queries over the final graph.

\subsection{Team Roles}

The repository and report follow the coursework's team-role model.

The domain expert --- \textbf{Abdrakhman Salmenov}, defined the scope and kept documentation coherent;

The modelling experts --- \textbf{Aditya Ranjan }and\textbf{ Kasim Morsel}, designed the ontology, mappings, queries, and evaluation methodology;

The data-ingestion/LLM pipeline experts --- \textbf{Yingtao Zheng} and \textbf{Immanuel Fradinho Oliveira}, implemented collection, extraction, cleaning, completion, and automation scripts.

\subsection{Requirements and Tech Stack}

\begin{itemize}[leftmargin=*,nosep]
    \item \textbf{Programming language:} Python.
    \item \textbf{Knowledge graph stack:} RDF, Turtle, SPARQL, \code{rdflib}.
    \item \textbf{Sources:} Guardian API (textual), Wikidata SPARQL endpoint (structured), NewsAPI (supplementary).
    \item \textbf{LLM integration:} OpenAI structured outputs with JSON-schema validation and local caching.
    \item \textbf{Project artefacts:} ontology in \filepath{ontology/news_ontology.ttl}, queries in \filepath{queries/news_competency_queries.rq}, prompts in \filepath{prompts/prompts.txt}.
    \item \textbf{Testing:} \code{pytest} suite covering ontology construction, extraction, normalisation, RDF conversion, completion, and query execution.
\end{itemize}

\subsection{Deviations from Original Specifications}

The current implementation is clearly a news-focused KG, but the repository still
contains a small amount of legacy prototype structure from an earlier
technology-oriented extractor. This is visible in \filepath{src/config.py}, where
backwards-compatibility aliases and older keyword groups were retained to avoid
breaking the pipeline while the final domain shifted to UK politics and policy
news. Rather than fully rewriting the prototype from scratch, the team stabilised
the working pipeline and aligned the final ontology, mappings, and queries to the
politics domain.

Another practical deviation concerns source balance. NewsAPI developer-tier access
returns only the first 100 results, so in the evaluated run it contributed only
3 retained articles, while the Guardian supplied 255. To strengthen the structured
data path, the project added Wikidata as the primary structured data source,
querying the public SPARQL endpoint for UK politicians, political parties, and
government bodies. These entity records are mapped directly to RDF without NLP,
complementing the textual extraction pipeline over Guardian article body text.

\section{Data Source Selection}\label{sec:data_sources}
%------------------------------------------------------------------

\subsection{Textual and Structured Sources}\label{sec:data_collection}

The coursework requires at least one textual data source and one structured data
source. This project satisfies that requirement through three complementary sources:

\begin{itemize}[leftmargin=*,nosep]
    \item \textbf{Textual data source --- Guardian API:} The Guardian API returns full
    article body text via the \code{bodyText} field. This unstructured natural-language
    content is the primary input for NLP-based extraction: named-entity recognition,
    topic assignment, event detection, sentiment classification, and article subtype
    inference. Collection is implemented in \filepath{src/data_collection.py}.
    \item \textbf{Structured data source --- Wikidata SPARQL endpoint:} The pipeline
    queries the public Wikidata Query Service for UK politicians, political parties,
    and government bodies. These typed entity records have explicit fields (name,
    party, constituency, gender, date of birth, founding date, headquarters) that map
    directly to ontology classes and properties without any NLP processing. Collection
    is implemented in \filepath{src/wikidata_collection.py}; direct RDF mapping is
    implemented in \filepath{src/wikidata_to_rdf.py}.
    \item \textbf{Supplementary source --- NewsAPI:} NewsAPI provides structured article
    metadata from multiple UK publishers. These records are normalised into the shared
    article schema alongside Guardian articles and follow the same extraction pipeline.
    NewsAPI broadens publisher coverage but is limited by developer-tier API access.
\end{itemize}

Article collection produced 258 articles (255 from the Guardian, 3 from NewsAPI).
Wikidata collection produced approximately 5,600 politicians, 960 political parties,
and 150 government bodies. Raw snapshots are saved under \filepath{data/raw/} for
offline reruns.

\subsection{How the Sources Were Selected}

The specification allows LLMs and web search to help identify relevant sources, as
long as the queries and prompts are documented. The project keeps these prompt logs
in \filepath{prompts/prompts.txt}. The Guardian API was chosen for its full article
body text, which enables genuine textual extraction. Wikidata was chosen as the
structured source because it provides typed entity records for UK political actors
through a public SPARQL endpoint, requiring no API key and enabling direct
field-to-property RDF mapping. NewsAPI was retained as a supplementary source for
publisher diversity.

\section{Extension of Existing Ontologies}\label{sec:ontology_design}
%------------------------------------------------------------------

\subsection{Reused Ontologies}

The ontology is generated programmatically in \filepath{src/build_ontology.py}
and written to \filepath{ontology/news_ontology.ttl}. It extends
Schema.org and BBC Core Concepts with a local \code{news:} namespace for
domain-specific classes and properties. These reused ontologies are directly aligned
with the chosen domain:
\begin{itemize}[leftmargin=*,nosep]
    \item \textbf{Schema.org} for articles, people, organisations, publishers, and article metadata.
    \item \textbf{BBC Core Concepts} for event and place modelling in a news setting.
\end{itemize}

\section{Competency Questions}\label{sec:cq}
%------------------------------------------------------------------

The coursework requires 20 competency questions: 10 manually produced and 10
generated with LLM assistance. This project follows that structure. Ten questions
were elicited manually from the domain requirements, and ten more were generated
with prompt support and then revised manually to ensure they were relevant,
non-duplicative, and answerable from the planned KG.

The prompt used for competency-question augmentation is documented in
\filepath{prompts/prompts.txt}. The resulting questions are operationalised by the
20 SPARQL queries stored in \filepath{queries/news_competency_queries.rq}.

\section{Mappings}\label{sec:mappings}
%------------------------------------------------------------------

\subsection{Extraction and Normalisation}\label{sec:extraction}

The processing pipeline is orchestrated by \filepath{src/main.py}. After source
records are normalised, \filepath{src/data_extraction.py} constructs KG-ready
records by combining heuristic extraction with optional OpenAI-assisted extraction.

The heuristic layer identifies:
\begin{itemize}[leftmargin=*,nosep]
    \item people, organisations, and locations through controlled lists plus regex patterns;
    \item topics through weighted keyword groups defined in \filepath{src/config.py};
    \item article subtype as \code{NewsArticle}, \code{OpinionArticle}, or \code{BreakingNewsArticle};
    \item sentiment as \code{Positive}, \code{Negative}, or \code{Neutral};
    \item event candidates such as \code{Election}, \code{Budget}, or \code{Policy Announcement}.
\end{itemize}

The OpenAI layer in \filepath{src/openai_client.py} uses strict JSON-schema
formats for both extraction and completion. Responses are validated before use and
cached under \filepath{data/cache/openai/} so that later runs can reuse previous
outputs. If the OpenAI client is unavailable, the pipeline falls back to heuristic
results without failing end to end.

\subsection{Mapping Structured and Textual Sources to the KG}

The specification notes that mapping structured data and mapping text require
different techniques. The project addresses that directly through two separate
mapping paths:
\begin{itemize}[leftmargin=*,nosep]
    \item \textbf{Textual mapping (Guardian articles):} heuristic and LLM-assisted
    extraction from article body text into entities, topics, sentiment, article
    subtype, and event candidates, followed by RDF conversion in
    \filepath{src/json_to_rdf.py}.
    \item \textbf{Structured mapping (Wikidata entities):} direct field-to-property
    conversion from Wikidata SPARQL results into RDF triples. Each entity field
    (name, party, constituency, gender, date of birth, headquarters) maps to a
    specific ontology class or property without NLP. Implemented in
    \filepath{src/wikidata_to_rdf.py}.
\end{itemize}

\subsection{RDF Construction and Completion}\label{sec:rdf_completion}

RDF instance generation is implemented in \filepath{src/json_to_rdf.py}. The
prototype graph is then enriched by \filepath{src/complete_kg.py}, which adds
or refines graph content using a constrained completion stage. This enrichment
focuses on sentiment, section labels, article subtypes, additional topics, inferred
word counts, update timestamps, and editorial follow-up links.

\section{Queries}\label{sec:queries}
%------------------------------------------------------------------

\subsection{SPARQL Query Layer}\label{sec:cq_method}

The project defines 20 competency questions, implemented as 20 SPARQL queries in
\filepath{queries/news_competency_queries.rq}. Ten were written manually and ten
were generated with LLM assistance and then revised manually. Prompt logs are kept
in \filepath{prompts/prompts.txt}. Query execution is handled by
\filepath{src/run_queries.py}, which stores results in \filepath{output/query_results.json}
and a timestamped output file.

\subsection{Prompt Use}\label{sec:prompts}

Eight prompts were explicitly versioned and reused:
\begin{itemize}[leftmargin=*,nosep]
    \item initial pipeline planning;
    \item competency-question augmentation;
    \item ontology review against reused vocabularies;
    \item source-to-ontology mapping draft;
    \item completion gap analysis;
    \item evaluation methodology design;
    \item LLM-assisted entity and event extraction (runtime);
    \item LLM-assisted KG completion (runtime).
\end{itemize}
This prompt use was supportive rather than autonomous: outputs were revised by the
team and encoded into the implemented ontology, mappings, code, and report.

\subsection{Strengths and Error Analysis}

Manual audit notes in \filepath{docs/evaluation_results.md} indicate that the KG is
most reliable for article metadata, publisher and author information, broad topic
assignment, article subtype, sentiment, and coarse event grouping. This is
consistent with the implementation: these fields are either mapped directly from
source metadata or validated against constrained vocabularies.

The weaker areas are also clear:
\begin{itemize}[leftmargin=*,nosep]
    \item person and organisation extraction sometimes over-generate because of regex matching;
    \item some location labels are noisy;
    \item event labels such as ``Policy Announcement'' remain generic;
    \item follow-up links are editorial heuristics rather than ground-truth relations;
    \item the article corpus is Guardian-dominated, though Wikidata provides broad structured entity coverage independently.
\end{itemize}

\subsection{Completion Impact}

Completion improves graph density without changing the overall ontology. The clearest
measurable gain is follow-up coverage: \ns{hasFollowUp} increases from 14 links in
the prototype KG to 90 links in the completed KG. Sentiment and event coverage are
also maintained consistently at graph level because completion adds validated values
instead of free-form text.

\subsection{Performance and Comparison Criteria}

The specification asks for both performance-oriented and quality-oriented evaluation.
This report therefore treats evaluation along two axes:
\begin{itemize}[leftmargin=*,nosep]
    \item \textbf{Performance and reproducibility:} whether the pipeline can run end to end, save intermediate artefacts, and rerun from cached snapshots and cached OpenAI outputs.
    \item \textbf{Quality:} whether the completed KG answers the competency questions, how clean those answers are, and where graph quality remains limited by noisy extraction or source imbalance.
\end{itemize}

The evaluation design also follows the coursework suggestion of comparing KG-based
answers with simpler direct LLM answering. The discussion in
\filepath{docs/evaluation_results.md} frames the KG as more reproducible and
traceable, while direct prompting is more fluent but less auditable.

\section{Testing}\label{sec:testing}
%------------------------------------------------------------------

The repository includes an automated \code{pytest} suite under \filepath{tests/}.
These tests do not prove extraction correctness exhaustively, but they do provide
useful regression coverage over the implemented pipeline stages.

\begin{itemize}[leftmargin=*,nosep]
    \item \filepath{tests/test_build_ontology.py} checks ontology construction, subclass/subproperty alignment, and Turtle serialisation.
    \item \filepath{tests/test_pipeline.py} checks end-to-end flow from source normalisation to RDF generation on fixture data.
    \item \filepath{tests/test_queries.py} checks that all 20 query definitions load and execute stably.
    \item Additional tests cover collection, extraction, normalisation, completion, RDF generation, and smoke-level repository behaviour.
\end{itemize}

This testing setup is especially valuable because the system combines deterministic
code with optional LLM-assisted stages. The tests enforce that the deterministic
fallback path remains usable even when the OpenAI client is unavailable.

\section{Conclusions}\label{sec:conclusions}
%------------------------------------------------------------------

The coursework repository delivers a working automated KG pipeline for UK politics
and policy news. It collects articles, builds a domain ontology, extracts and
normalises article content, converts the data to RDF, enriches the graph through a
constrained completion stage, and answers 20 competency questions with SPARQL.

The most defensible conclusion is not that the KG is perfect, but that it is
successful, reproducible, and queryable. Its strongest outputs are structured
metadata and broad analytical relations; its remaining weaknesses lie in entity
precision, generic events, follow-up semantics, and source imbalance.

\paragraph{Future Work.}
The next improvements are clear from both the code and evaluation: add provenance
for completed triples, improve named-entity precision with stronger disambiguation,
link article-extracted person mentions to Wikidata entities for cross-source entity
resolution, and replace heuristic follow-up links with better evidence-grounded
editorial progression modelling.

%------------------------------------------------------------------
\section{Project Management}\label{sec:management}
%------------------------------------------------------------------

The repository is organised to support reproducibility and division of work. Source
code lives in \filepath{src/}, ontology files in \filepath{ontology/}, query files
in \filepath{queries/}, prompt logs in \filepath{prompts/}, evaluation notes in
\filepath{docs/}, and automated tests in \filepath{tests/}. This separation is one
of the project's practical strengths because it keeps modelling artefacts, code, and
evaluation evidence versioned together.

\paragraph{Risks and Mitigations.}
The main project risks were API availability, noisy extraction, and non-determinism
from LLM assistance. These were mitigated through raw-data snapshotting, strict
schema validation of OpenAI outputs, local caching of responses, deterministic
fallback heuristics, and automated regression tests.

%------------------------------------------------------------------
\section{AI Usage}\label{sec:ai_usage}
%------------------------------------------------------------------

AI tools were used in a constrained and supportive role. OpenAI was integrated into
the implemented system for structured extraction and completion, but only through
schema-constrained JSON outputs that were validated before being merged into the KG.
Separate prompt use supported competency-question ideation, ontology review, mapping
design, completion analysis, and evaluation planning.

The key point is that AI outputs were not treated as authoritative free text. They
were either revised manually for coursework artefacts or passed through explicit
validation logic in the codebase before becoming part of the final graph.
